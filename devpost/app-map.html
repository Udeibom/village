Village — app map

Lesson plans that fit the room you actually have. Village writes a lesson with an AI, then checks its own work with plain JavaScript before it is allowed to say the lesson is ready to teach.

Take-home reference, generated from the code at commit 2c0d94c. A snapshot — it can drift as the code changes.

The app in three pieces

  1. The teacher page — one screen: the lesson request, the classroom reality, the materials list, and the Generate button that stays disabled until there is a curriculum objective and one material to check against.
    src/App.jsx, src/components/
  2. The writer — Groq, in strict JSON mode, with a repair retry when the reply does not fit the shape. It writes; it never judges its own work.
    server/grok.js
  3. The checker — plain functions, no AI: materials against the inventory, timings against the lesson length, the assessment against the objective, and the curriculum claim.
    shared/validate.js
  4. The classroom — what this teacher owns, what worked, and what a colleague proved elsewhere. Kept on the teacher's own device, never on a server.
    src/lib/store.js, src/lib/bank.js, src/lib/reuse.js, src/lib/lessonCard.js

What changed after the first five slices

The core — write, check, rebuild, edit, print — was finished first. Then the scope was widened, and these are the parts a chat window structurally cannot follow:

  • The classroom is remembered. The shelf, the classroom's record and the curriculum document live in localStorage (src/lib/store.js), with a "Forget this classroom" button.
  • "How did it go?" The teacher marks a lesson as worked, changed or failed (src/lib/bank.js, src/components/OutcomeStrip.jsx), and it is banked with its date, its class size and where it came from.
  • The next lesson is planned around what worked before — and the rules for that are code, not the model's judgement (src/lib/reuse.js): proved here, materials on the shelf, class size and lesson length within a quarter, the activity no more than 60% of the budget, same subject and year group.
  • A proven lesson travels as one small file (src/lib/lessonCard.js), labelled as a candidate until it is proved in the receiving classroom.
  • The curriculum check uses the teacher's own document (shared/curriculum.js): the objective is searched for in their pasted or uploaded extract, and the row quotes the line it found. With a document present, the document decides.
  • The timings are fitted in code (server/timing.js): the model's minutes are scaled onto the lesson's budget, and the panel says so.
  • It works with no internet. The kernel moved to shared/ so the browser runs the same checker as the server (src/lib/localCheck.js). Checking, editing, the record and the print-out all work offline; only writing a new lesson needs a connection.

A 4-stop route through the code

A reference route — follow it if you want to see the whole path for yourself. The teacher in this project has already run it live, so this is a pointer, not a test.

1. The button that cannot be pressed yet

src/lib/formRules.js → canGenerate(form)

The rule that keeps Generate disabled until there is a curriculum objective and at least one material lives here, in one plain function, so it can be tested without a browser. src/App.jsx reads it and sets disabled on the button.

2. The part that must not lie

shared/validate.js → checkLesson(lesson, form)

Four checks, each returning its own pass/fail and a plain-language line for the teacher: checkMaterials (peak simultaneous need, not a sum), checkTiming (2-minute tolerance, under 60% fill fails), checkAssessment (does the assessment test the objective), checkCurriculum (what Village can and cannot confirm about curriculum). No AI is involved anywhere in this file — that is the whole point.

3. The rule for what may be reused

src/lib/reuse.js → findReusableActivity(bank, form)

Which of the teacher's own proved activities fits the lesson being planned. It is decided by plain rules — proved here, every material on the shelf now, class size and lesson length within twenty-five per cent, the activity no more than sixty per cent of the budget, the same subject and year group — and the objective only decides which candidate wins. The model is told what to reuse; it is not asked to decide.

4. The loop that keeps trying

server/rebuild.js → buildLessonWithRebuilds(...)

Write, check, and if something is short, rebuild the lesson around what is actually on the table — at most MAX_REBUILDS = 2 times. The generator and the rebuilder are passed in as arguments, so the whole loop can be tested with fakes in scripts/verify.js without spending a single API call.

To change this, start here

  • The wording of the lesson, or what the model is told to do → buildGenerationPrompt and buildRebuildPrompt in server/grok.js. Both take the teacher's form, so the instructions change in one place. npm run ai-check shows what the model then actually produced.
  • What the classroom knows → src/lib/bank.js and src/lib/reuse.js. The record of what was taught, what worked, and the rules that decide what may be planned again.
  • What may be said about the curriculum → shared/curriculum.js. The search through the teacher's own document, and the rule that the document decides whenever there is one.
  • A rule about what counts as enough → shared/validate.js. requiredMaterials works out the peak simultaneous need, parseQuantity decides what can be counted, objectivesMatch and matchingKey decide whether the assessment really tests the objective. Every rule there has a case in scripts/verify.js.
  • What the teacher sees in the panel → src/components/FeasibilityPanel.jsx. The wording of each verdict and each check line is here, in plain language, next to the check it belongs to.
  • What the teacher can edit, and what stays put → src/components/LessonPlan.jsx. Dotted lines are editable; the assessment block is tagged Village checks this one because the checker reads what the assessment claims to test.
  • The printable page → src/components/PrintView.jsx and the @media print block at the end of src/styles.css.

A practice to reuse

The moment: a live Groq run produced an assessment that said it tested “students will demonstrate understanding by correctly forming and comparing ratios” while the teacher's objective was “understand and represent ratios”. The checker called that a mismatch and told the teacher the lesson needed attention. It was wrong.

How it was settled: by reading the two texts and asking which side was at fault — the model, or the checker. The assessment did test the objective, so the checker was comparing too literally. The fix was in matchingKey (shared/text.js, used by shared/validate.js): words are compared on their first four letters, so “comparing” and “compare” are the same word.

Where it is kept: the live failure is a permanent case — “an assessment that describes the objective in its own words still counts” in scripts/verify.js, with a second case beside it (“an assessment that uses its own verbs still counts”) covering a different pair of words. Break matchingKey — change the four-letter rule back to return word — and those two cases fail, which is how you know the check can fail at all.

How to reuse it: when a check fails on real output, decide which side is wrong before changing either, and make sure the check is capable of failing. A checker that cannot fail is not evidence of anything, and a prompt tuned against one happy path will meet the next teacher immediately.

Running it again

cd village
npm install
cp .env.example .env     # then paste your GROQ_API_KEY into .env
npm run dev             # page on http://localhost:5173, API on :3001

Checks, in the order worth running them:

npm run verify         # 114 assertions on the rules — no browser, no API calls
npm run browser-check  # 50 checks driving the real app in headless Chrome (stubbed, free)
npm run ai-check       # a live run against Groq — costs a little money
